# 策略说明：BTC/ETH Maker Rebate Assistant

## 1. 这个项目解决什么问题

做市商需要同时管理 BTC 和 ETH 的双边被动报价。难点不是简单地“多挂订单”，而是：

1. 报价太远，几乎没有成交；
2. 报价太近，容易被主动交易者挑走，成交后马上产生亏损；
3. LONG/SHORT 库存失衡后，继续补单会放大风险；
4. 趋势行情中仍然双边报价，会不断接住逆势仓位；
5. 撤改单过于频繁，会浪费订单额度并触发限频；
6. maker rebate 看起来为正，但扣除逆向选择和资金成本后可能为负。

本项目的目标是：在 Hedge Mode 下批量生成 BTC/ETH 的 Post-Only 报价意图，并先判断这批报价是否值得运行。

当前版本是模拟和研究版本，不会直接向交易所下单。

## 2. 一轮批量计划怎么产生

```text
MarketSnapshot
  -> 交易对筛选
  -> 行情状态判断
  -> 返佣边际判断
  -> LONG/SHORT 库存判断
  -> 生成报价层
  -> 全局订单和名义仓位拦截
  -> 输出 OrderIntent
```

输入是一组 `MarketSnapshot`，至少包含：

- 中间价、买一、卖一；
- 买卖两侧盘口名义深度；
- 24 小时成交额；
- 波动率；
- 资金费率；
- 交易状态。

输出是 `BatchPlan`，包含每个交易对的状态、报价、订单意图、阻塞原因、总订单数和总名义仓位。

## 3. 交易对筛选

`score_symbol()` 先过滤不适合做市的市场：

- 不是 `TRADING`；
- 24 小时成交额太低；
- 买卖价差超过阈值；
- 任一侧盘口深度缺失；
- 资金费率过高。

通过筛选不等于一定下单，只代表它进入下一步评估。

## 4. 行情状态

系统把行情分成五类：

- `range`：允许双边报价；
- `trend_up`：减少 SHORT 开仓，只保留有限 LONG 买单；
- `trend_down`：减少 LONG 开仓，只保留有限 SHORT 卖单；
- `shock`：暂停新报价；
- `unknown`：数据不足，暂停新报价。

状态判断使用 K 线收盘价、EMA 关系、价格斜率、近期高低点和 ATR 百分比。它不是预测价格，而是决定当前是否适合双边做市。

## 5. 报价如何计算

报价宽度不是固定的止盈金额，而是：

```text
raw_width = max(基础宽度, 当前盘口价差 + 波动率补偿)
width = min(raw_width, 最大报价宽度)
```

然后加入两项修正：

### 盘口深度修正

如果买方深度明显强于卖方，系统会对报价中心做轻微微价格偏移，避免永远围绕简单中间价报价。

### 库存偏移

```text
inventory_ratio = 当前库存名义价值 / 最大库存名义价值
inventory_skew = inventory_ratio × 报价宽度 × 系数
```

库存为正时，卖价更容易成交、买价更远；库存为负时相反。

## 6. Hedge Mode 的 LONG/SHORT 逻辑

正常震荡时：

- 买单使用 `positionSide=LONG`，代表建立多头库存；
- 卖单使用 `positionSide=SHORT`，代表建立空头库存。

当多头库存超过净仓位阈值：

- 卖单切换成 `positionSide=LONG`；
- 设置 `reduce_only=True`；
- 目的变成减少多头，而不是继续开空。

当空头库存超过阈值：

- 买单切换成 `positionSide=SHORT`；
- 设置 `reduce_only=True`；
- 目的变成回补空头，而不是继续开多。

这部分是本轮最重要的修复，避免把 Hedge Mode 的减仓单错误地当成反向开仓单。

## 7. 为什么不无限增加订单

系统同时限制：

- 每侧报价层数；
- BTC/ETH 总订单数；
- 总 gross notional；
- 总 net notional；
- 单个交易对库存；
- 单日亏损和波动率。

如果批量计划超过任意全局限制，整批计划会被标记为 `blocked`，不会继续增加订单。

## 8. 返佣是否真的值得

系统不只看 maker rebate，而是估算：

```text
net_estimate = maker rebate
             - adverse selection
             - funding cost
             - operational cost
```

其中：

- maker rebate：预计真实 maker 成交额 × 返佣费率；
- adverse selection：成交后价格向不利方向移动的估计成本；
- funding cost：永续合约资金费率造成的成本；
- operational cost：运行和请求成本。

净收益估算不为正时，计划应被视为不可行。

## 9. 为什么要限制刷新频率

报价不是每次行情轮询都撤掉重挂。`should_refresh()` 只有在以下情况发生时才刷新：

- 中间价移动超过阈值；
- 行情状态变化；
- 报价超过最大存活时间。

这可以减少：

- 无意义的撤改单；
- 订单额度浪费；
- API 限频风险；
- 报价状态和交易所状态不一致。

## 10. 如何判断优化是否有效

不能只看“挂了多少单”。需要记录：

- maker 成交率；
- maker 成交额；
- rebate 收入；
- 成交后固定窗口的逆向选择损失；
- 实现价差；
- 平均库存和最大库存；
- 平均订单存活时间；
- 撤改单次数；
- 429/网络错误次数；
- 扣除资金费率后的净收益。

只有真实历史盘口或 Testnet 结果显示净收益为正，才有理由进一步考虑生产接入。

## 11. 当前还没有做什么

以下功能仍然必须在实盘前完成：

- Binance `exchangeInfo` 精度和过滤器校验；
- 用户数据流订单对账；
- 部分成交和未知状态恢复；
- STP 参数适配；
- 请求限频和退避；
- 断线重连；
- reduce-only 最终校验；
- 保证金监控和 kill switch。

因此 `makerlab/live.py` 会阻止真实提交订单。它的存在是为了明确边界，而不是假装已经完成实盘。
